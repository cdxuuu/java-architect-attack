## 一、JVM 调优参数全解（Day01）

### 差距1.1：参数与版本演进的对应关系不熟
> Day1发现，延续第5周差距3.4 / 4.5 / 6.3

- **现状**：知道 JDK 8 用 `-XX:+PrintGCDetails`、JDK 11+ 用 `-Xlog:gc*`，但 CMS 各版本演进（JDK 9 Deprecated / JDK 14 移除）、BiasedLocking 在 JDK 15 废弃（JEP 374）、ZGC 在 JDK 15 转正等版本边界细节不熟
- **架构师水平**：能脱口而出 JDK 8 / 11 / 17 / 21 各版本参数差异表；能在 JDK 升级评审时 30 分钟内列出所有需要迁移的参数；能用 `jcmd PID VM.flags` 验证参数实际生效情况
- **补足方向**：精读 JEP 291（CMS Deprecated）/ JEP 363（CMS 移除）/ JEP 374（Biased Locking Deprecated）/ JEP 377（ZGC Production）/ JEP 439（分代 ZGC）；在测试环境跑一次 JDK 8 -> 17 参数迁移演练

### 差距1.2：MaxGCPauseMillis 的"目标 vs 上限"陷阱不深
> Day1发现

- **现状**：知道 `-XX:MaxGCPauseMillis=50` 是"目标"，但实际生产中"G1 没达到目标该怎么调"的工程经验不足，经常误以为"设小就有效"
- **架构师水平**：能讲清 MaxGCPauseMillis 与 G1NewSizePercent / G1MaxNewSizePercent / IHOP / G1ReservePercent 的耦合关系；能在 30 分钟内画出"调参耦合矩阵"；能根据 GC 日志反推哪个参数需要调整
- **补足方向**：第 2 周 Day05 实测 G1 调优时建立"调参矩阵"；调研 Netflix / LinkedIn 的 G1 调优案例；阅读 R大博客关于 G1 自适应调优的 3 篇文章

### 差距1.3：指针压缩 32GB 边界的实战经验不足
> Day1发现

- **现状**：知道 32GB 是指针压缩边界，但"31GB 堆 vs 33GB 堆"的实测性能差异、为什么"32GB 堆 + 单实例"不如"30GB 堆 + 多实例"、JDK 15+ 的指针压缩新特性（HotSpot 仍维持 32GB）不深
- **架构师水平**：能用 JMH 实测 24G / 30G / 32G / 36G 堆的吞吐与 GC 停顿曲线；能在容量规划阶段决定"大堆单实例 vs 小堆多实例"
- **补足方向**：用 IM 网关做一次 24G vs 32G 实测；调研 Azul Zing / Prime 的"无指针压缩限制"方案；阅读 OpenJDK `compressedOops.cpp` 源码

### 差距1.4：容器化 JVM 参数的实战坑不熟
> Day1发现，延续第3周（7月第3周 K8s）差距3.7 / 6.2

- **现状**：知道 `-XX:+UseContainerSupport` 默认开启，但 cgroup v2 兼容性、CPU Throttling 对 JVM Safepoint 的影响、`-XX:ParallelGCThreads` 在容器中为什么要手动设的工程经验不足
- **架构师水平**：能讲清 JDK 8u191 之前的两个经典容器问题（内存不看 limit / CPU 不看 limit）；能诊断 CPU Throttling 引发的偶发 P99 飙高；能根据 K8s `requests/limits` 精确推算 JVM 参数（`-XX:InitialRAMPercentage` / `-XX:MaxRAMPercentage`）
- **补足方向**：在 K8s 集群实测 cgroup v2 下 JVM 行为；调研 Google Cadvisor / kubelet cgroup 监控；阅读 JEP 343（Packaging Tool）与容器化演进

### 差距1.5：JIT 参数与 GC / Safepoint 的协同不深
> Day1发现，延续第5周差距5.7

- **现状**：知道 `-XX:+TieredCompilation` / `-XX:CompileThreshold`，但分层编译开启后实际触发 C1/C2 的阈值（Tier 3 约 200 次 / Tier 4 约 10000-15000 次）、JIT 编译线程占 CPU 与 GC Safepoint 的交互不深
- **架构师水平**：能用 `-XX:+PrintCompilation` 跟踪 100 个方法的编译历史；能诊断"JIT 编译线程占 30% CPU"的异常；能设计预热方案避免冷启动 JIT 抖动
- **补足方向**：阅读 OpenJDK `compileBroker.cpp` / `simpleThresholdPolicy.cpp`；调研 AppCDS / AOT 编译在 JDK 17 的实战；用 JMH 测试预热前后的性能差异

### 差距1.6：-XX 陷阱与生产配置模板的实战经验不足
> Day1发现

- **现状**：知道开关型（`+`/`-`）与赋值型（`=`）区别，但 `-XX:+DisableExplicitGC` 的副作用（Direct ByteBuffer 清理失效）、`-XX:+UseStringDeduplication` 的适用场景、`-XX:+HeapDumpOnOutOfMemoryError` 的磁盘预留计算等工程经验不足
- **架构师水平**：能为不同业务场景（IM / 视频 / 监管 / 历史归档）定制生产配置模板；能 30 分钟内排查"配置了 OOM 自动 dump 但没生效"的问题（路径权限 / 磁盘满 / 容器 rootfs 不可写）
- **补足方向**：整理团队 JVM 生产配置模板库；调研阿里 / 美团 / 字节跳动的 JVM 参数规范；在测试环境复现"DisableExplicitGC 导致 Direct ByteBuffer OOM"

### 差距1.7：JVM 内存规划的全局视角不足
> Day1发现，延续第4周简历项目差距1.5

- **现状**：能估算堆 / 直接内存 / 元空间的基础占用，但 Code Cache / Thread Stack / GC 日志 / Heap Dump 预留 / JVM 自身开销（约 200-500MB）的全局视角不足，导致 K8s limit 设得偏小被 OOM kill
- **架构师水平**：能为 4C8G / 8C16G / 16C32G Pod 设计标准 JVM 内存配比模板；能用 NMT（Native Memory Tracking）精确测算 JVM 自身开销
- **补足方向**：用 `jcmd PID VM.native_memory summary` 实测 IM 网关的 JVM 内存构成；调研 Netflix 容量规划方法论；为在线问诊系统设计 3 套标准 Pod 配比

## 二、JVM 诊断工具链实战（Day02）

### 差距2.1：JDK 自带命令行工具的版本差异不熟
> Day2发现

- **现状**：知道 jps / jstat / jmap / jstack 基础用法，但 JDK 8 vs JDK 11+ 的工具差异（jmap 大堆卡死 vs jcmd 稳定 / jhat 废弃 / JFR 开源）不熟；`jstack -F` / `-l` / `-m` 各选项的适用场景容易混淆
- **架构师水平**：能不查文档直接写出 `jcmd PID GC.heap_dump /tmp/x.bin` / `jstack -l PID` / `jstat -gcutil PID 1000 10`；能讲清为什么 JDK 11+ 推荐 jcmd 而非 jmap；能用 JFR 替代传统 jstack/jmap 做持续低开销采样
- **补足方向**：每日练 1 个工具（周一 jstack、周二 jmap、周三 jcmd、周四 JFR、周五 jstat）；阅读 OpenJDK `serviceability` 模块源码；在测试环境复现"jmap 在 32GB 堆上卡死"

### 差距2.2：Arthas 命令的熟练度不足
> Day2发现，延续第4周简历项目差距

- **现状**：知道 Arthas dashboard / thread / jad / watch / trace 基础用法，但 vmtool / ognl / redefine / profiler 等高阶命令不熟；`watch` 表达式语法（`params` / `returnObj` / `target` / `#cost`）容易写错；`trace -n N` 限制次数的工程实践不足
- **架构师水平**：能用 `vmtool --action getInstances --className com.github.benmanes.caffeine.cache.BoundedLocalCache` 直接查缓存实例；能用 `ognl '@com.example.Config@DEBUG = true'` 不重启改日志级别；能用 `redefine` 热更新字节码（含限制：不能改方法签名 / 字段 / 继承关系）
- **补足方向**：精读 Arthas 官方文档高级用法；每周练 2 个高阶命令；调研 Arthas 在 K8s sidecar 模式的部署最佳实践

### 差距2.3：MAT 堆内存分析的深度不足
> Day2发现

- **现状**：知道 Histogram / Dominator Tree / Leak Suspects 三大视图，但 Shallow Size vs Retained Size 的本质区别、`Path to GC Roots` vs `Merge Shortest Paths` 的适用场景、OQL 查询语法、10GB+ 大 dump 的处理方法不深
- **架构师水平**：能用 OQL `SELECT s.size FROM java.util.HashMap s WHERE s.@retainedHeapSize > 1000000` 查大 Map；能配置 MAT `-Xmx20g` 处理 10GB dump；能 1 分钟内从 Dominator Tree 找到 Retained Top 1 元凶
- **补足方向**：精读 Eclipse MAT 官方文档；本地装 MAT 实战 3 个真实 dump；调研在线 MAT（heapdump.io）的隐私合规问题

### 差距2.4：jstack + 火焰图实战经验不足
> Day2发现，延续第5周差距7.3

- **现状**：知道 `top -Hp` + `printf %x` + jstack 的 5 步法，但火焰图解读能力不足（"宽且尖"vs"宽且平"的判断）、async-profiler 的 4 种模式（cpu / alloc / lock / wall）的适用场景、JFR 持续录制的生产配置不熟
- **架构师水平**：能在 5 分钟内从火焰图找出 CPU 占 80% 的单一热点方法；能用 `async-profiler -e alloc` 找出内存分配压力大的方法；能为生产服务配置 JFR 持续录制（maxage=1h / maxsize=200M）
- **补足方向**：本地装 async-profiler 实战 5 个火焰图；调研 Netflix FlaPoodle 火焰图产品；阅读 Brendan Gregg 火焰图论文

### 差距2.5：GC 日志分析的实战经验不足
> Day2发现，延续第5周差距2.5

- **现状**：知道 JDK 8 用 `-XX:+PrintGCDetails`、JDK 11+ 用 `-Xlog:gc*`，但 G1 Mixed GC 日志中 `[Pause (G1 Evacuation Pause) (young) (initial-mark) (mixed)` 各字段含义、`to-space exhausted` 的诊断、gceasy.io 在线分析的关键指标（Throughput / Avg Pause / Max Pause）的实战经验不足
- **架构师水平**：能 30 秒内从 GC 日志判断"Minor GC 频繁 / Mixed GC 慢 / Full GC 失败"三类问题；能用 GCViewer 离线分析 1 周 GC 日志找趋势；能为生产服务设计 GC 监控告警（堆 > 85% / Full GC > 1次/分钟）
- **补足方向**：收集 5 份真实生产 GC 日志做分析练习；用 Filebeat + ES + Kibana 搭建 GC 日志监控；调研 Datadog / Dynatrace 的 GC 监控产品

### 差距2.6：5 分钟定位 Full GC 元凶的节奏感不足
> Day2发现，延续第5周差距7.4

- **现状**：知道"5 分钟定位"的思路，但实际生产中"分秒级"动作清单（0:00-0:30 现象确认 / 0:30-1:00 止损决策 / 1:00-2:00 抓现场 / 2:00-3:00 日志分析 / 3:00-4:00 堆分析 / 4:00-5:00 根因止血）的节奏感不足；"摘流量 + 抓 dump"的执行顺序容易出错（先抓 dump 会 STW 引发雪崩）
- **架构师水平**：能背出 5 分钟定位法的 6 个节奏点；能在 30 秒内做止损决策（摘流量 / 限流 / 降级 / 重启）；能 1 分钟内抓完 jstack + jmap dump + GC 日志三件套
- **补足方向**：每月一次故障演练（注入内存泄漏）；整理团队"5 分钟定位 SOP"；调研 Google SRE 故障排查手册

### 差距2.7：工具链副作用的工程意识不足
> Day2发现

- **现状**：知道 jmap / jstack / Arthas 有副作用，但 `jmap -histo:live` 触发 Full GC、`jstack -F` 挂起进程、`Arthas trace` 高 QPS 长挂导致 RT 飙高、`Arthas redefine` 反复试错导致 Metaspace 膨胀等副作用的实战意识不足
- **架构师水平**：能为每个工具建立"副作用清单"与"何时禁用"判断标准；能在生产事故中快速决策"用哪个工具副作用最小"；能用 `monitor` 替代 `watch` 降低开销
- **补足方向**：整理团队"工具链副作用速查表"；在测试环境实测 Arthas trace 在 1000 QPS 下的 RT 影响；调研阿里 / 美团的工具链使用规范

### 差距2.8：工具链体系建设不足
> Day2发现，延续第5周差距6.5 / 7.3

- **现状**：会使用单个工具，但"工具链体系建设"（JFR 长开 / Arthas sidecar / dump 路径预留 / 监控告警 / 故障知识库 / 定期演练）的架构师视角不足
- **架构师水平**：能为团队设计完整的 JVM 工具链体系（持续录制 + 自动告警 + 故障自愈）；能搭 Arthas tunnel server 集中管理多 Pod；能设计混沌工程演练机制
- **补足方向**：调研 Datadog APM / Dynatrace 的 JVM 监控产品；搭建 IM 网关的工具链体系 PoC；调研 Netflix Chaos Monkey 故障注入实践

### 差距2.9：K8s 容器内工具链使用经验不足
> Day2发现，延续第3周（7月第3周 K8s）差距

- **现状**：知道 `kubectl exec` 进 Pod 用 Arthas，但 K8s 1.12+ 共享 PID namespace 的 sidecar 模式、Arthas tunnel server 远程连接、init container 注入 Arthas 等 K8s 原生方式不熟

- **补足方向**：在测试 K8s 集群搭建 Arthas sidecar PoC；调研阿里 ACK / 字节 TKE 的 JVM 诊断产品；阅读 K8s 1.25+ ephemeral container 文档
