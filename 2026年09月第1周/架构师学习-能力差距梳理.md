## 一、网络编程模型演进（Day01）

### 差距1.1：长连接容量量化能力不足
> Day1发现，延续第4周简历项目差距（容量规划）

- **现状**：知道"BIO 不行、NIO 行"，但说不出每长连接 10~50KB 的构成（fd + 内核 socket buffer + Session 对象）、线程栈 1MB 默认值、上下文切换 1~10μs 的量级；面试官量化追问时只能定性回答
- **架构师水平**：30 秒内完成"峰值 50w 在线 → 单机 10w → 5 台 + 30% 余量"的内存/带宽/连接数三维容量推算
- **补足方向**：给 IM 在线客服项目做一次完整容量估算，写进简历项目的"容量规划"段落；核对 Linux 默认参数（ulimit -n / threads-max / Xss）

### 差距1.2：epoll 机制理解止步于数据结构名词
> Day1发现

- **现状**：答"epoll 快"只到"红黑树"，说不出"回调挂就绪链表"（ep_poll_callback → rdllist）这个真正机制；说不出"100% 活跃时 epoll 无优势"的反向边界；存在"epoll 用 mmap"的八股错误认知
- **架构师水平**：画得出"网卡中断 → 软中断 → 协议栈 → ep_poll_callback → 就绪链表 → epoll_wait 返回"完整链路；能按系统 IO 活跃度分布做 select/poll/epoll 选型判断
- **补足方向**：把回调链路画图讲一遍；记住"稀疏活跃用 epoll"与活跃度分布的因果关系

### 差距1.3：LT/ET 与阻塞/非阻塞两组概念混淆
> Day1发现，延续并发周 Day05 差距（虚拟线程调度）

- **现状**："ET 才要非阻塞"是对的，但"LT 语义的 JDK Selector 为什么也要求非阻塞 fd"答不出；ET 不读完丢事件的两种形态（没读到 EAGAIN 中途返回、读一半来了新数据无新跳变）说不全
- **架构师水平**：因果分离——ET 要非阻塞是为了"读完不挂死"，事件循环要非阻塞是为了"一个线程伺候多个连接不卡队"，两个理由独立成立
- **补足方向**：用 ET + 阻塞 fd 手写一次 read 循环，亲测 EventLoop 挂死现象

### 差距1.4：Buffer 状态机与半包累积的实操能力不足
> Day1发现

- **现状**：只会背"flip 翻转"，说不出不 flip 的具体症状（从 pos 写到 limit，写出空洞字节）与不 compact 的症状（半包数据被 clear 作废）；自己写解码器必错
- **架构师水平**：手写"定长头 + 变长体"协议的裸 NIO 接收循环（只用 compact + 累积缓冲）一次跑通，作为 Day03 粘包拆包的前置练习
- **补足方向**：Day03 之前完成该练习；把 flip/rewind/clear/compact 四操作的状态变化写成卡片

### 差距1.5：零拷贝只会背名词，画不出路径图
> Day1发现，延续 MQ 周差距（Kafka 高性能原理）

- **现状**：说不出"传统 4 次拷贝 4 次切换 → sendfile 2 次拷贝 2 次切换"的完整路径（DMA/CPU 拷贝分别标不清）；不知道 sendfile 只有 file→socket 方向；串不起 Kafka（sendfile）与 RocketMQ（mmap）的选型差异
- **架构师水平**：白板画两条数据流向路径图；讲清 DMA gather 从页缓存直取的机制；与 Day04 Netty 的 CompositeByteBuf/slice（应用层零拷贝）分层说清
- **补足方向**：画路径图进笔记；对照 Kafka FileRecords 与 RocketMQ MappedFile 源码入口各读一遍

### 差距1.6：heap buffer IO 隐性拷贝与 Netty 内存池因果链不熟
> Day1发现，延续 JVM 第2周 Day05 差距（堆外内存）

- **现状**：不知道 heap ByteBuffer 做 socket IO 时 JDK 会偷偷拷贝到临时 DirectByteBuffer（Util.getTemporaryDirectBuffer）；"Netty 为什么力推 direct + 池化"的因果链讲不完整；direct 内存不占堆但要占容器内存预算的账容易漏算
- **架构师水平**：背熟因果链——heap 隐性拷贝 → direct 免拷贝 → direct 分配贵（失败触发 System.gc）→ PooledByteBufAllocator → 引用计数 → ResourceLeakDetector；K8s memory limit 公式纳入 MaxDirectMemorySize
- **补足方向**：读 sun.nio.ch.IOUtil 源码；把因果链与 JVM 堆外内存周的事故案例对上

### 差距1.7：网关选型叙事缺乏结构，虚拟线程问题答成二极管
> Day1发现，延续并发周 Day05 差距（虚拟线程）

- **现状**："为什么用 Netty"讲不出三层对比（Tomcat 容器抽象错位 / WebFlux 多付响应式复杂度 / 自研痛点清单=工作量清单）；虚拟线程会不会替代 Netty 答"会"或"不会"，不会分"线程模型层"与"框架能力层"两层回答；不知道虚拟线程网络 IO 底层就是 epoll（sun.nio.ch.Poller）
- **架构师水平**：从协议、容量、生态、团队四个维度展开选型叙事；虚拟线程问题分层回答并点出 io_uring + 虚拟线程的未来组合
- **补足方向**：把 Day01 第 6 问的两张对比表内化成面试话术，结合 IM 网关项目练 STAR 叙述
